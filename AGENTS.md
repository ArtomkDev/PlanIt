# PlanIt Repository Instructions

## Start with repository context

- For substantial work, run `git status --short` before editing. Treat every existing change and untracked file as user work until its ownership is established.
- When `graphify-out/graph.json` exists, use `npm.cmd run graphify:query -- "<question>"` before broad searches for architecture, feature flow, or file relationships. Use `npm.cmd run graphify -- path "<A>" "<B>"` or `npm.cmd run graphify -- explain "<concept>"` for focused relationships. Fall back to targeted `rg` and source reads when the graph lacks detail.
- Inspect the implementation and nearby files before proposing or writing code. File and directory names alone are not evidence of purpose.

## Project architecture

PlanIt is an Expo/React Native application with native Android/iOS and React Native Web targets.

- `index.js` registers the Expo root and the Android widget task. `App.js` delegates to `src/Root.jsx`.
- `src/Root.jsx` owns authentication/guest routing, deep links, top-level providers, analytics, and the root navigation container. `src/layouts/MainLayout.jsx` and `src/navigation/` compose the main Schedule, Tasks, and Settings experience.
- Keep reusable UI in `src/components/`; feature screens and feature-local UI in `src/pages/`; shared hooks in `src/hooks/`; application state/providers in `src/context/`; data access and side-effecting domain operations in `src/services/`; pure/shared logic in `src/utils/`; app constants and integration setup in `src/config/`; translations in `src/locales/`; and widget code in `src/widgets/`.
- Preserve established platform splits such as `.native`, `.web`, and `.android` modules. Check for an existing platform implementation before adding a branch or new file.
- Schedule data and synchronization are centered on `ScheduleProvider`, `src/config/firestore.js`, storage/sync utilities, and the existing service layer. Do not introduce a second global store, sync engine, storage wrapper, or Firebase access layer for an already-owned responsibility.
- Firebase client setup lives in `src/config/firebase.js`; Firestore behavior and rules live in `src/config/firestore.js`, `firestore.rules`, and `storage.rules`. Server code is the separate Node 22 ESM package under `functions/`.
- `app.config.js` and `plugins/` are the durable sources for Expo/native configuration. `android/` and `ios/` are generated by Expo prebuild and ignored; prefer config plugins over hand-editing generated native output unless the task explicitly targets generated native files.
- `content/legal/` is the source for legal content. `src/config/legalDocuments.generated.js` is generated by the `legal:*` scripts; do not hand-edit it.
- Root tests use Node's test runner with `.cjs` fixtures and targeted `test:*` package scripts. Firebase Functions have their own `check` and `test` scripts in `functions/package.json`. There is no repository-wide lint or typecheck script; do not claim one was run.
- `dist/`, `builds/`, `.expo/`, `.firebase/`, native build output, dependencies, credentials, and Graphify caches are local/generated areas with different purposes. Never delete them merely because they are ignored. `graphify-out/graph.json`, its report, manifest, labels, learning data, and query memory are intentional repository tooling.

## Preserve the existing architecture

Before creating a component, hook, context/provider, service, utility, manager, helper, configuration module, or abstraction:

1. Query Graphify or search for the responsibility and likely synonyms.
2. Inspect the nearest implementation, its callers, tests, and platform variants.
3. Reuse or extend the existing owner when that keeps one source of truth.
4. Create a permanent file only when it has a distinct architectural responsibility and belongs in an existing project location.

Do not build parallel systems for state, persistence, synchronization, authentication, attachments, notifications, navigation, theming, localization, Firebase access, or widgets. Do not move code into a new layer solely to make a small change look structured.

## Change discipline

- Make the smallest coherent change that fully solves the task.
- Do not refactor, rename, move, reformat, or modernize unrelated code.
- Preserve public behavior and data formats unless the task requires a change. Treat synchronization, migrations, account deletion, authentication, attachments, notifications, and generated native configuration as high-risk paths requiring focused tests.
- Match nearby naming, import style, component patterns, state management, error handling, and file organization. Do not impose a new style on one file.
- Preserve user changes. Never use `git reset --hard`, `git clean -fd`, or broad checkout/restore commands to obtain a clean tree.

## Production code quality

- Write concise, direct code that resembles the strongest nearby human-written code.
- Comments should explain only non-obvious intent, constraints, platform quirks, or workarounds. Avoid line-by-line narration, obvious JSDoc, tutorial prose, and comments that restate the code.
- Avoid speculative abstractions, needless wrappers, one-use factories/managers/adapters, helpers that obscure simple logic, and duplicated fallback paths.
- Handle plausible failures at the layer that can recover or add useful context. Do not add broad `try/catch` blocks that swallow errors, defensive checks for impossible states, or silent fallbacks that hide defects.
- Leave no dead or commented-out code, unused imports/variables, temporary feature flags, debug logging, placeholder copy, or test-only behavior in production paths.
- Reuse existing theme tokens, localization utilities, UI primitives, services, and platform guards instead of duplicating them.

## Temporary work and repository hygiene

- The repository root is never a scratch directory. Do not create `.codex-*`, verification exports, copied apps, review bundles, screenshots, debug dumps, or one-off scripts there.
- Prefer a unique directory under the operating system temp directory for exports, screenshots, generated comparisons, and experimental scripts. Pass that path through the tool's supported output option and remove it after verification.
- If a tool must write inside the repository, use its established ignored cache/output location and remove only the exact artifacts created by the current task. Do not change application output paths merely to satisfy this rule.
- Do not add an ignore rule to conceal task debris. An ignored path still requires cleanup when it is temporary.
- Do not delete untracked or ignored content based only on its name. Inspect contents, references, Git tracking, and build/runtime use first. Preserve existing release binaries, credentials, local native projects, and user-created artifacts unless the task explicitly owns them.

## Verification and completion

- Run the narrowest relevant checks. Use the existing root `test:*` scripts, `npm.cmd run legal:check` for legal content/generator changes, and `npm.cmd --prefix functions run check` plus `npm.cmd --prefix functions test` for Functions changes.
- Use build/export verification only when it adds confidence for the affected path. Direct disposable output to the OS temp directory when the tool supports it.
- After source changes, run `npm.cmd run graphify:update-code` to refresh the local AST graph without credentials. Use `npm.cmd run graphify:update` when changed docs/images also need semantic indexing and a supported backend is configured. Review resulting graph changes along with the source changes.
- Before completion, inspect the diff and run `git status --short`. Account for every modified, added, deleted, and untracked path.
- Remove temporary files and accidental generated output created by the task. Recheck for unused imports/variables, debug logging, dead code, temporary helpers, and unjustified permanent files.
- A task is not complete while its scratch files remain in the repository or while unrelated user changes have been overwritten.
